# Wolverine (outbox/inbox over RabbitMQ)

## Topology in AspireBoot
- **Api** = publisher. Entity changes and outgoing messages commit in ONE PostgreSQL transaction (EF Core outbox). Wolverine relays them to RabbitMQ afterwards.
- **Worker** = consumer. Durable inbox (dedup by message ID), handlers, retries, scheduled jobs.
- Both persist envelopes in PostgreSQL in **separate schemas** (`wolverine_api`, `wolverine_worker`) to avoid collisions.
- Message contracts live in `Core/Messaging/<Context>/` as immutable `sealed record`s with only IDs and data needed (no entities, no secrets).

## Configuration essentials
```csharp
builder.Host.UseWolverine(opts =>
{
    opts.PersistMessagesWithPostgresql(cs, "wolverine_api");
    opts.Services.AddDbContextWithWolverineIntegration<AppDbContext>(x => x.UseNpgsql(cs));
    opts.UseEntityFrameworkCoreTransactions();
    opts.Policies.AutoApplyTransactions();
    opts.UseRabbitMqUsingNamedConnection("rabbitmq").AutoProvision(); // dev; prod: explicit setup
    opts.Policies.UseDurableOutboxOnAllSendingEndpoints();   // Api
    opts.Policies.UseDurableInboxOnAllListeners();           // Worker
    opts.MultipleHandlerBehavior = MultipleHandlerBehavior.Separated;
    opts.Services.CritterStackDefaults(x =>
    {
        x.Production.GeneratedCodeMode = TypeLoadMode.Static;
        x.Production.AssertAllPreGeneratedTypesExist = true;
        x.Production.ResourceAutoCreate = AutoCreate.None;
    });
});
```
- Append `Keepalive=30;Tcp Keepalive=true` to the PostgreSQL connection string used by Wolverine. Do not use PgBouncer in transaction mode.
- Explicit publish routing per message type (`PublishMessage<T>().ToRabbitExchange(...)`) and durable queues (RabbitMQ 4.3 rejects non-durable non-exclusive queues).
- Production: `TypeLoadMode.Static` with code generated by `dotnet run -- codegen write` in the Docker build stage, and schema/broker provisioned explicitly (`dotnet run -- resources setup`) as a deploy step. Never `UseResourceSetupOnStartup()` in production (it clears envelopes). Dev needs `WolverineFx.RuntimeCompilation`.
- Do not connect to DB or broker before `RunJasperFxCommands(args)`.

## Publishing from an API slice
- Inject `IMessageBus` (or return cascading messages) inside a handler/endpoint whose DbContext transaction Wolverine manages, or use `IDbContextOutbox<AppDbContext>` + `SaveChangesAndFlushMessagesAsync()` in plain Minimal API endpoints.
- **Never publish directly to RabbitMQ** or before the DB commit.

## Handlers (Worker slices)
- One slice folder per message: `Worker/Identity/SendEmail/SendEmailHandler.cs`, with a public class `SendEmailHandler` and a method `Handle(SendEmailMessage msg, ..., CancellationToken ct)`. Static handlers are fine.
- **Idempotent by design** (redelivery happens): check state before acting, and use natural keys.
- Validation failure in a handler means log + discard (no HTTP semantics).
- Scheduled/recurring: `opts.Schedules.ScheduleRecurring<CleanupOrphanAvatarsMessage>("0 3 * * *")` with `SkipWhileRunning()`. Missed runs are skipped.

## Errors and retries
- Global: transient DB/network errors → `RetryWithCooldown(50ms, 250ms, 1s)` with jitter, then `MoveToErrorQueue()`. Invalid input → `Discard()`.
- Use a circuit breaker on listeners talking to fragile externals (SMTP).
- `Fault<T>` events include plaintext message data. Do not enable them for messages carrying PII.

## Transactions
- Eager (default) is required if the handler uses `ExecuteUpdate`/raw SQL. Do not combine Eager with EF `EnableRetryOnFailure()`.
- Multiple DbContexts need an explicit `[Transactional(typeof(AppDbContext))]`.

## Observability
- `tracing.AddSource("Wolverine")`, `metrics.AddMeter("Wolverine*")`. Trace context propagates through envelopes, so an API request trace continues into the Worker handler.
- Set `opts.Tracking.RecordExceptionsOnSpans = false` if messages could carry sensitive data in exceptions.

## Health
- `AddHealthChecks().AddWolverine()` (live+ready) and `.AddWolverineListeners()` (ready only).

## Testing
- `host.TrackActivity().Timeout(30.Seconds()).IncludeExternalTransports().InvokeMessageAndWaitAsync(msg)`, or `ExecuteAndWaitAsync(...)` around an HTTP call to assert messages `Sent`/`Executed`.
- Shared host fixtures: `host.ClearAllWolverineStorageAsync()` between tests. Warm up handlers in Dynamic mode to avoid timeouts.
- CI: `opts.AssertNoCombinedHandlers()`.
